# loadsim —— 多 session 实时双工压测

MiniCPM-o 的实时双工服务,一个 worker 同时挂着多个会话。要回答的问题是:并发到多少
会开始扛不住,以及是「算不过来」还是「供应不上实时」。

已有的压测脚本都是单会话的:连一个 worker,发一段固定音频,看每一轮的耗时拆解。
这套工具补的是另一个维度——把会话数量、会话**什么时候上来**、**上来之后怎么说话**
都变成可控的参数,并且观测端到端的结果,而不是单轮耗时。

## 为什么需要它

同一台机器上,「8 个会话同时连上」和「8 个会话在前 60 秒里陆续连上」是两件完全
不同的事。前者把 8 份冷启动开销叠在同一瞬间,后者每个会话都在别人已经跑热的系统上
开始。把并发当唯一变量的压测,测出来的数字既不对应任何一种真实流量,也无法说明
服务在真实到达模式下还剩多少余量。

具体到实时语音,还有一层:客户端的体感不取决于平均延迟,而取决于**播放缓冲有没有
见底**。服务端可以算得慢一点,只要音频缓冲还够播,用户听不出来;缓冲一见底,声音
就断了。所以这套工具的主指标是断流时长占会话时长的比例,不是延迟均值。

## 用法

```bash
cd omni-perf-op/loadsim
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"

# 1. 自检:起一个假服务端,不碰 GPU,确认工具本身没问题
.venv/bin/python -m loadsim.cli selftest --concurrency 8 --duration 30

# 2. 发压机自证:确认这台机器的客户端在目标并发下自己不断流
.venv/bin/python -m loadsim.cli burn --concurrency 100 --duration 20

# 3. 对真实服务发压
.venv/bin/python -m loadsim.cli run \
    --url ws://127.0.0.1:8006/v1/realtime?mode=audio \
    --arrival poisson --concurrency 8 --duration 300 \
    --lifetime-mean 60 --lifetime-dist lognormal \
    --reuse \
    --user-audio ../MiniCPM-o-Demo/tests/cases/common/user_audio/000_user_audio0.wav \
    --out results/poisson-c8.json
```

第二步容易被跳过,但省掉它的代价是整场压测的结论作废,而且作废得很难发现:报告里的
数字看起来完全正常,只是它们量的是发压机而不是服务端。`burn` 把服务端换成一个不做
任何限速的本地桩,同样的并发下客户端自己不该有任何断流;如果这一步就断了,瓶颈在
发压机侧,后面测到的断流不能算在服务端头上。

`:8006` 是 demo 的 gateway 端口。对 worker 直连也可以,但那样绕过了排队与 worker
分配,测不到容量瓶颈真正暴露的那一层,所以默认应当连 gateway。

并发升高时,gateway 的队列是第一个饱和点:worker 全忙时新会话会停在队列里,先体现
为排队等待变长,队列长度超过上限后直接拒绝。所以「能建多少会话」和「建起来之后
跑得好不好」是两个独立的容量问题,报告里把它们分开统计就是为了能区分这两者。

## 三个会显著改变结果的参数

### 1. 到达模式 `--arrival`

会话不是同时上线的。可选:

| 模式 | 含义 | 什么时候用 |
|---|---|---|
| `poisson` | 到达间隔服从指数分布。排队论的标准模型,也是 vLLM 压测 `--request-rate` 的口径 | 默认。瞬时并发有涨落,接近随机接入 |
| `ramp` | 会话均匀铺在到达窗口内。闭环工具(Locust、k6 的 ramping VUs)的做法 | 要一条可比的回归基线,爬升过程确定、无随机抖动 |
| `burst` | 一半会话在开头几秒内成批上线 | 复现尖峰:推送、整点活动、散会时一群人同时进 |
| `trickle` | 每个会话在窗口内均匀随机取一个时刻 | 比斜坡更松,观察会话互相错开时的稳态成本 |
| `all_at_once` | 全部同一时刻上线 | 最坏情况:冷启动开销完全叠加 |

### 2. 会话时长 `--lifetime-mean / --lifetime-dist`

控制一个会话占住 worker 多久。有 `lognormal`(默认)、`exponential`、`weibull`、
`fixed` 四种。真实通话时长是右偏的——多数几十秒结束,少数拖到几分钟——对数正态比
指数分布更贴近,指数分布的尾巴更重。`--lifetime-max` 要设成不超过服务端的硬上限
(video 300 秒、audio 600 秒),否则会话会被服务端以 timeout 关闭,把正常超时算进
错误率。

### 3. 要不要补位 `--reuse`

这一项决定「并发」这个概念在你的压测里能不能成立,同时也决定这次压测是开环还是闭环——
这是推理压测里比「选哪个分布」更本质的一条分界。

不补位是**开环**:你配置的是到达率,系统自己决定堆起多少并发。不补位时你写的
`--concurrency` 实际是**一共投几个会话**,不是**同时有几个**。并发由到达率和会话时长
共同决定(排队论里的 Little 定律:稳态并发 ≈ 到达率 × 平均时长),并且会先爬到峰值
再随会话各自结束而下降,峰值取决于这次抽到多长的会话。工具会在事前检查这个关系,
达不到目标并发时会直接打印警告并给出该改哪个数。

补位是**闭环**:你配置的是并发,系统顶着这个并发跑。会话一退场就补一个新的,实际并发
稳定在目标值附近。爬升阶段会按「占空比」多开一些槽位:会话平均跑 60 秒、退出后平均
3 秒补上,那么一个槽位只有约 95% 的时间真的被占用,只开目标并发那么多个槽位,实际
并发就会稳定地低一截。`--retry-mean` 控制补位延迟,`--abandon` 控制用户退出后不再
重连的概率(大于 0 时并发会随时间下滑,用于观察服务在负载回落时的表现)。

这两种口径测的不是一回事,不能互相替代:开环才能暴露排队,闭环测的是峰值容量。
同一份配置两种都跑一次,差异本身就是结论。

### 4. 说话节奏 `--talk-* / --pause-*`

默认值出自电话语音的实测,不是估的:Lee & Un 1986(IEEE Trans. Comm. 34(6))在
50 分钟电话语音上测得平均说话段 1.11–1.30 秒、平均静音 2.22–2.41 秒、语音活动比
31.5%–37.8%。工具默认按这组数取,实际活动比约 0.39。

这一组比直觉值低得多,值得写下来:拍脑袋设成「说话段 3 秒、静音 1.75 秒」的话,
活动比是 0.63,上行负载差不多是真实情况的两倍,压出来的容量会明显偏悲观——而且偏得
看不出来,因为数字本身完全正常。`--barge-in` 控制抢话概率,命中时静音被截断到近零。

## 观测什么

每次运行输出一份 JSON,外加终端上的汇总表和并发曲线。几个关键量:

- **断流时长占比**(`starve_ratio_*`)——播放缓冲见底的时间占会话时长的比例。
  这是主指标。0 表示全程没断过;超过百分之几,语音听起来就开始有断续。
- **断流会话占比**(`starving_session_ratio`)——有断流的会话占多大比例。均值可能
  好看,但只要有 20% 的会话在断,那就是 20% 的用户在骂。
- **实际并发**(`concurrency_peak` / `concurrency_steady_mean` / 曲线)——用来核对
  这次压测到底压到了多少。它和你配置的目标值不是一回事。
- **建会话延迟 / 排队等待**(`setup_latency_*` / `queue_wait_*`)——并发升高时先变
  差的是这两个,它们比吞吐更早暴露容量不足。
- **失败构成**(`failure_breakdown`)——连接失败、握手超时、服务端 error、排队过久
  分开计数。混成一个「错误率」会掩盖「容量不足」和「服务崩了」的区别。

### 帧长与决策延迟

上行帧长由 `--frame-ms` 控制,默认 80 毫秒。80 是 OpenAI Realtime 默认 server VAD 的
分块粒度,但 MiniCPM-o 的产品前端实际发的是 1000 毫秒一帧,模型每秒决策一次。按 80 毫秒
发,服务端每秒要做 12.5 次决策而不是 1 次,压出来的容量比真实流量低得多。所以压容量
时应当加 `--frame-ms 1000`,让每个会话对服务端的压力与真实前端一致;80 保留为默认值
只是为了与已有的自检、发压机自证和验证记录对得上。

每一帧都有一条决策延迟:从第 k 个 `input.append` 发出,到收到第一条 `response_id`
以 `_resp_<k>` 结尾的 listen 或 text delta。audio delta 是 TTS 异步吐的,不算决策。
这个量直接回答服务端有没有跟上帧节奏:决策落后于一帧,后面的帧就开始排队。汇总里的
`decision_p50_s / decision_p95_s / decision_p99_s / decision_max_s` 是把所有会话的所有
帧合在一起算的分位数,不是逐会话分位数再平均;`decision_over_budget_ratio` 是超过预算
的帧占比,预算由 `--decision-budget-ms` 给,默认等于帧长。服务端如果在 delta 的
`metrics` 里带了自己的 `prefill_ms` 和 `generate_ms`,也会一并收下来(`server_decode_ms_*`),
用来区分「决策慢是排队慢还是算得慢」。会话结束时还没等到决策的帧记在
`frames_unanswered`。内置假服务端不给 `response_id` 编号,所以 selftest 里这几栏是空的。

汇总末尾有一个 `verdict`,pass 的条件是:没有失败会话、没有排队超时、决策延迟 p95 不超过
预算、断流会话占比不超过 5%。任一条不满足就是 fail,`verdict_reasons` 列出具体是哪几条。
前两条是「服务还扛得住」的底线;p95 不超过一帧是项目里多 session 容量压测判到顶的判据;
5% 沿用 `burn` 子命令的口径。阈值集中在 runner.py 顶部的几个常量里。并发扫描脚本读
这一个字段就够,不必自己再定判据。

## 跑压测的纪律

三条不是可选项,跳过任意一条都会让结论作废,而且是静静地作废——报告里的数字看起来
完全正常。

**一、不同并发之间用全新进程单独跑。** 不要在一个进程里顺序扫 32、64、96、128。
Metronome(唯一公开按 session 数报实时双工容量的工作)公开订正过一次由此产生的
错误结论:一次 90 秒的扫描显示某个并发下容量崩溃,后来发现是「顺序扫描 + 外部 GPU
争用」的产物,单点重跑就平了。

**二、跑够时长。** Metronome 记录的漂移数据是:同一份负载,每帧 p50 在头 30 秒是
2–5 毫秒,到 270–300 秒涨到 1601 毫秒,而这三五分钟里延迟指标全程健康。实时双工的
典型失败模式是「短时高并发没事、几分钟后垮」,只跑 30 秒的压测看不见它。默认时长
应当拉到几分钟。

**三、报容量必须绑定配置。** 同一个模型在不同的 KV 策略下容量能差 2 到 6 倍,
所以在 demo 默认配置下压出来的数字,只能配上「这是 demo 默认配置下的数」这句话,
不能当作模型的固有容量。

## 模型的边界

说清楚它不做什么,比说清楚它做什么更重要,不然容易拿它去解释它解释不了的现象。

- **上行是固定音频的循环与拼接**,不区分内容。模型侧的 SPEAK/LISTEN 决策由音频内容
  驱动,所以这套工具测的是**服务容量**,不是模型行为。用它得出的结论里不能包含
  「模型会说多少话」这类判断。
- **不做播放、不管音频质量**。断流是按「收到多少秒音频、过了多少秒墙钟」算出来的,
  与音频听起来如何无关。
- **播放缓冲模型是乐观估计**。它假设客户端一收到音频就能播,不做前置缓冲;真实
  客户端要多攒几百毫秒才起播,实际断流只会比报告里的数字更严重。
- **补位模型是近似**。它按「会话结束 + 指数延迟」的节奏补位,而不是模拟真实用户
  按兴趣决定要不要重连。它保证并发层面的形状正确,不保证用户行为的因果正确。
- **单机单进程发压**。一台机器能压出的并发受限于它自己的 CPU 与网络。实测(Apple
  Silicon 笔记本、单个 Python 进程、假服务端不做任何限速):150 路并发跑满 20 秒,
  零失败、零断流,建会话延迟 p95 为 90 毫秒。也就是说这台机器本身的发压能力远高于
  150 路,几百路以内不需要担心客户端成为瓶颈。但真正要压到这个量级时,读数之前
  应当先做一次这样的空转自证:把服务端换成不做限速的桩,确认同样的并发下客户端
  自己不断流,否则测出来的断流分不清是服务端的还是发压机自己的。
- **发压机与服务端之间的网络也是被测链路的一部分**。跨机房压测时,上行音频的
  排队延迟会体现在建会话延迟和断流里。要区分,就在不同网络位置各发一次压。

## 播放缓冲模型

`PlaybackBuffer` 是一个库存模型:

- 收到一秒音频就多一秒库存
- 过了一秒墙钟就烧掉一秒库存
- 库存为负说明没货可播,负到多少就是已经断流多久

**关键设计**:区分两种状态:

1. **speaking**(有 audio delta 下发):tick 消耗库存,见底算断流
2. **listening**(收到 `kind=listen`):暂停 tick,不消耗库存,等下一轮 audio delta

这是双工协议的核心语义:`kind=listen` 表示「模型进入倾听状态,客户端应当停止播放」。不处理 listen 会把协议正常的倾听状态误判成断流。

## 测试

```bash
.venv/bin/python -m pytest loadsim/tests -q     # 单元测试,不需要 GPU
.venv/bin/python -m loadsim.cli selftest        # 对本机的假服务端发压
.venv/bin/python -m loadsim.cli burn --concurrency 100   # 发压机自证
```

单元测试钉住的是三类容易悄悄错掉的事:

- 泊松到达的平均间隔必须等于 1/到达率,否则实际压的并发和标称的对不上;
- 补位模式必须按占空比超配,否则实际并发稳定偏低;
- 播放缓冲的断流判定不能因为浮点尾差把健康会话报成断流。

另外钉住两条口径:默认说话节奏的语音活动比要落在电话语音实测的区间内(拍脑袋设成
说话段三五秒会让上行负载翻倍,而且偏得看不出来);排队等不到 worker 属于容量不足,
要和连接失败、服务端报错分开统计,混成一个失败率会把处置方向带偏。

**对真实服务发压必须在有 GPU 的开发机上做**,自检和发压机自证可以在任何机器上跑。
端到端验证的完整方法与结果见 `docs/e2e-validation.md`。

## 验证数据

对 MiniCPM-o 的服务端链路实测,记录在 `docs/e2e-validation.md`。那一轮用的是确定性
后端替身(真 gateway、真 worker,只有模型换成固定公式),所以数字反映的是链路与
生命周期,不是模型推理速度:

| 场景 | 说明 |
|---|---|
| 单会话 | 建会话 0.13 s,首帧音频 0.06 s,零断流 |
| 4 路并发打单 worker | 排队 0/35/70/105 s 的等差序列,与 gateway 日志逐条吻合 |
| 同配置重跑三次 | 计数类指标逐字节相同,延迟类毫秒级抖动 |
| 假服务端 selftest | 并发升高时故意变慢,用于确认工具能识别真断流 |

**listen 事件的语义处理**是实测中最容易出错的一处。双工协议里 `kind=listen` 表示
模型进入倾听状态,客户端应当停止播放、暂停消耗缓冲。不处理它,会把「模型正常在听」
算成断流——修复前单会话压测报 80% 以上断流,修复后为 0%。

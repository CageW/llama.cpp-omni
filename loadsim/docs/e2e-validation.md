# 端到端验证记录

2026-09-16。验证对象:`omni-perf-op/loadsim/` 这套多 session 压测工具。
验证范围:**单会话协议链路正确性**与**可复现性**。

---

## 验证为什么不能只看工具自己的输出

工具的单元测试跑的是它自己的假服务端。假服务端按工具的假设写,工具再按自己的假设
核对,两边同时错也能对上。所以真正的验证必须让工具面对**它没有参与编写的服务端代码**,
并且用**独立于工具的记录**去核对。

这次用的独立记录有两个:gateway 自己的日志(谁在什么时候被分到哪个 worker、排在队列第几位),
以及服务端侧独立累加的计数。工具的读数与这两者逐项对照。

---

## 环境

按仓库约定,开发与测试都在开发机 uds-dev1 上跑(本机 Mac 无 GPU、且没有到内网的
路由,在本机得出的结论无效)。

服务端用的是 demo 仓库自己的三个进程,没有换实现:

- `gateway.py`——真 gateway,负责排队、worker 分配、WebSocket 转发
- `worker.py`——真 worker,负责会话状态机与后端桥接
- `loadsim/docs/stub_backend.py`——替换掉 `py_backend/server.py` 的确定性后端

**为什么换掉后端而不是跑真模型。** 卡在 GPU 上:LIS 生产集群的 H20 全部在用,
开发集群 cls-a3mkfr2v 的两台 PRO5000 也在跑别的服务。而更根本的是,这次要验的是
工具的**协议与生命周期**——什么时候该等 `session.queue_done`、init 之后多久才来
`session.created`、音频 delta 按什么节奏吐——这些全在真 gateway 与真 worker 里。
模型算多快本来就是要被压测测出来的量,不是校验工具正确性的基准,换成固定公式反而
让结果可复现。这个替换写明了,不假装它是真模型。

后端公式:单会话基础产出速率 1.35 倍实时,每多一个并发会话衰减 11%,
建会话开销 0.10 秒加并发数乘 0.02 秒。全部写死,所以同一配置重跑可复现。

## 一、协议链路正确性

### 1.1 会话生命周期与时序

单会话跑 35 秒,工具上报:

| 量 | 工具上报 | 服务端侧独立记录 | 是否一致 |
|---|---|---|---|
| 会话建立成功 | 是 | gateway `Immediate assign → local-worker (type=audio_duplex)` | 一致 |
| 排队等待 | 0.0097 秒 | 无排队记录(立即分配) | 一致 |
| 建会话延迟 | 0.1343 秒 | 后端公式给 0.12 秒 | 量级一致 |
| 首帧音频延迟 | 0.0599 秒 | 一个 delta 周期 80ms 内 | 一致 |
| 会话正常结束 | `lifetime_expired` | worker 日志 `POST /sessions/sess_.../close 200 OK` | 一致 |

工具正确地等到了 `session.queue_done` 才发 `session.init`,没有抢跑;`session.created`
之后才开始上行。这两步的顺序错了的话,服务端会直接拒绝,压测根本跑不起来。

### 1.2 上行帧数(最容易做假的数)

工具报 355 帧 / 28.4 秒,平均每帧 80.0 毫秒——与工具声称的 80 毫秒帧长一致。

另写了一个**不依赖 loadsim** 的独立脚本,直接用 `websockets` 按协议连上去数一遍,
同样单会话 25 秒:数出 314 帧,平均 80.0 毫秒。两者在同一基准上吻合。

### 1.3 下行音频与播放缓冲

工具报该会话收到 469 个音频 delta。按每个 delta 80 毫秒算,共 37.5 秒音频,
而会话时长 28.47 秒,即服务端以 **1.32 倍实时**产出——与后端公式在零并发下应给的
1.35 倍吻合(差值来自建会话那 0.13 秒没有产出)。

断流时长 0.0 秒,与「产出速率大于实时、缓冲不会见底」的预期一致。

### 1.4 语音活动比

工具报 0.3549。这个数应当落在电话语音的实测区间内,因为工具的默认说话节奏就是按
那组实测值设的(Lee & Un 1986,语音活动比 31.5%~37.8%)。0.3549 在区间内,
说明工具确实按它声称的参数在发压,而不是只有配置写对了、实际没执行。

默认参数(说话段 0.6~1.8 秒均匀分布、静音段 1.2~2.6 秒均匀分布)计算出的理论
语音活动比为 **0.3871 = 1.2 / (1.2 + 1.9)**,正好落在实测区间 [0.32, 0.38] 内。
短会话(<30秒)的实测比会因统计涨落偏高,selftest 默认 15 秒跑出 0.40+ 是正常的。

## 二、可复现性

同一配置、同一随机种子跑三次,单会话 20 秒:

| 指标 | run a | run b | run c |
|---|---|---|---|
| 上行帧数 | 355 | 355 | 355 |
| 下行 delta 数 | 469 | 469 | 469 |
| 上行总时长(秒) | 28.4 | 28.4 | 28.4 |
| 其中用户说话(秒) | 10.08 | 10.08 | 10.08 |
| 语音活动比 | 0.3549 | 0.3549 | 0.3549 |
| 会话时长(秒) | 28.4702 | 28.4690 | 28.4685 |
| 建会话延迟(秒) | 0.1364 | 0.1337 | 0.1346 |
| 首帧音频延迟(秒) | 0.0599 | 0.0597 | 0.0598 |

**计数类与行为类的量逐字节相同**,延迟类在零点几毫秒到几毫秒之间抖动。
这正是应当出现的形态:同一种子决定的是投放计划与说话节奏(确定性的),不决定
服务的响应时间(它本来就受调度影响)。

另外单独核对了生成器本身的确定性:

- 同一随机种子两次生成的投放计划,**逐元素相同**;
- 泊松到达换种子后计划确实不同(说明种子真的在起作用,不是摆设);
- 补位模式的爬升段是固定间隔铺开的,所以换种子不影响它——这是设计如此,
  随机性在补位时刻与说话节奏上。

## 三、并发下的容量归因(附带结论)

这一项不在原定范围内,但单 worker 的排队行为正好可以用来说明工具如何区分
「容量不足」与「服务故障」。

同一个 worker,4 路并发,每路会话 35 秒:

| 会话 | 排队等待 | 建会话完成 | 会话时长 | 上行帧数 | 断流 |
|---|---|---|---|---|---|
| 0 | 0.011 秒 | 0.137 秒 | 35.18 秒 | 439 | 0 |
| 1 | 35.185 秒 | 35.310 秒 | 70.36 秒 | 439 | 0 |
| 2 | 70.368 秒 | 70.491 秒 | 105.54 秒 | 439 | 0 |
| 3 | 105.542 秒 | 105.667 秒 | 140.73 秒 | 439 | 0 |

会话 0 立即拿到 worker,之后每一个都要等前一个跑完它的整整 35 秒,排队时刻是
0 / 35 / 70 / 105 秒的等差序列。gateway 日志独立印证:1 个 `Immediate assign`,
其余 `Enqueued` 且位置依次为 1、2、3。gateway 自己估的 ETA 是 30.7 / 61.4 / 92.2 秒,
略低于实测,因为它按配置里的平均时长估,而这次会话时长是固定 35 秒。

**这条同时说明 demo 当前的并发模型**:一个 worker 同时只服务一个会话,
第 N+1 个会话必须排队等前一个结束。要让 N 个会话真正并行,需要 N 个 worker。
用 6 路并发打单 worker 时,6 个里只有 1 个立即拿到,其余 5 个排队 ETA 从 26 秒
起按每个 26 秒累加。

工具在这件事上的关键行为是**分类正确**。第一版把「在队列里等太久」报成
`handshake_timeout`,读报告的人会去查日志找服务端崩溃,而真正该做的是加 worker。
现已改成三类:

- `queue_timeout`——一直没排到 worker,是**容量不足**,单独统计,不计入失败率;
- `init_timeout`——排到了 worker 但建会话没完成,是**后端问题**;
- `closed_during_handshake` / `error`——连接层面的**故障**。

排队上限由 `--max-wait` 控制,默认 30 秒。压容量时应当显式调大:worker 全忙时
排队几十秒是正常现象,用默认值会把「在排队」误报成「服务无响应」。上面那次 4 路
测试把上限提到 150 秒后,失败率归零,全部会话按队列顺序正常跑完。

## 四、这次验证覆盖不到的部分

说清楚边界比报告通过更重要。

- **没有跑真模型。** 后端是确定性替身。模型推理的耗时分布、显存增长、KV 缓存
  压力这些,这次一个都没测到。要测这些必须在有 GPU 的机器上跑真服务。
- **没有验证过载下的断流归因。** 原计划的第三项范围没有做。要验证它,需要让
  服务端的产出速率掉到实时以下,而替身后端的衰减系数是写死的,不能用来冒充真实
  的过载行为。
- **没有覆盖 video 模式。** 只验了 `mode=audio`。video 模式的上行要带视频帧,
  工具目前只发送音频,压 video 需要扩展。
- **没有验证 gateway 的队列打满后的行为。** demo 的队列上限是 1000,这次并发
  远未触及,「队列满了会怎样」没有被测到。
- **wss 只在本地自签证书上验证过。** 三条 TLS 路径(不给 CA 被拒、给 CA 通过、
  `--insecure` 通过)都在本机用自签证书跑通了,但没有对真实的公网 TLS 端点验证过。

## 五、复现方式

```bash
# 开发机上
cd ~/omni-verify

# 1. 起确定性后端
.venv/bin/python loadsim/docs/stub_backend.py --port 22500 &

# 2. 起真 worker(指向后端)
cd MiniCPM-o-Demo
~/omni-verify/.venv/bin/python worker.py --host 127.0.0.1 --port 22400 \
    --gpu-id 0 --backend-server-url http://127.0.0.1:22500 &

# 3. 起真 gateway
~/omni-verify/.venv/bin/python gateway.py --host 127.0.0.1 --port 8006 --internal-port 8007 --http &

# 4. 注册 worker
curl -X PUT http://127.0.0.1:8007/internal/workers/local-worker \
    -H 'content-type: application/json' \
    --data '{"endpoint":"127.0.0.1:22400","gpu_group":"gpu-0"}'

# 5. 发压
cd ~/omni-verify && PYTHONPATH=. .venv/bin/python -m loadsim.cli run \
    --url "ws://127.0.0.1:8006/v1/realtime?mode=audio" \
    --arrival all_at_once --concurrency 4 --duration 120 \
    --lifetime-mean 35 --lifetime-dist fixed --max-wait 150 \
    --user-audio user_audio.wav --seed 20260915 --out /tmp/result.json
```

`--user-audio` 用的是 demo 仓库自带的素材
(`tests/cases/common/user_audio/000_user_audio0.wav`),不引入外部依赖。

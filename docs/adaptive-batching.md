# 自适应合批：让 executor 自己决定何时发 forward

2026-09-18。分支 `feature/adaptive-batch-scheduler`，基线 `feature/server-multisession`。
测试机：南京 H20 节点 `vm-7-13-ubuntu`，权重 MiniCPM-o-4.5 F16。压测工具 loadsim 在分支
`perf/realtime-load-simulator-adaptive`。

## 问题

多 session 时所有 session 的 LLM forward 走同一个共享 executor：每个 session 把自己的下一步
（一次 prefill 或一个 token 的 decode）投进队列，worker 线程把队列里的步合成一次 `llama_decode`。
合批的收益很陡：在 H20 上一次 1 token 的 forward 单独跑 6.8 ms，8 路合在一起 9.3 ms，16 路
11.7 ms，32 路 15.9 ms。也就是说宽度 16 时每路只摊到 0.7 ms，比单独跑便宜十倍。

但 worker「什么时候发」是几个启动时读死的参数决定的：等待窗口 3 ms，prefill 凑批目标数，
prefill 最长等待 200 ms。这套参数在两头都不对。负载低时窗口是纯粹的额外延迟；负载中等时
各 session 的步不是同时到的（每个 session 拿到结果后要在主机侧采样约 6 ms 才投下一步，
而各 session 的相位随机），3 ms 的窗口等不到别人，一轮本可合成一次的 forward 被拆成三四次
小的，GPU 时间花在固定开销上。负载高到队列永远非空时倒是自然合批了，但那时延迟已经超标。

benches 里之前的结论是「多等一会儿凑批的所有参数都更差」，原因是 decode 和 prefill 在同一个
队列里，凑 prefill 会把 decode 一起扣住。后来的 `ripe` 策略只扣 prefill 不扣 decode，把
单卡上限从 16 抬到 24，但它仍是固定阈值加固定 deadline，而且 decode 那一侧完全不合批。

## 做法

`OMNI_EXEC_POLICY=adaptive`。worker 在每次把结果交还给某个 sequence 时记下时刻，在该 sequence
下一次投步时算出「交还到再投」的间隔；只有间隔短于 60 ms 的算链内间隔（长于这个数说明它在等
客户端的下一帧，不是在采样），对每个 sequence 维护这个间隔的均值和平均绝对偏差。

队列非空时 worker 不立刻发，而是先看：哪些 sequence 刚拿到结果、还没投回来、按它自己的间隔
均值加两倍偏差算还没到期。这些是「马上会回来的」。等它们回来能省下的是 k 次 forward 的固定
开销；GPU 空闲时省下的 GPU 时间没有价值，所以按 GPU 忙占比加权。等待的代价是已经排队的步
多等 Δ。规则是 Δ 小于 k 乘固定开销乘忙占比乘增益（默认 1.5）时才等，等到第一个预测到达就
重新评估，任何一个已排队的步总共最多被扣 20 ms。GPU 忙占比是 forward 时间除以墙钟时间的
指数滑动平均，固定开销从单步单 token 的 forward 时间在线估计。

这和 Symphony（2023）的 deferred batching 是一个思路：按成本曲线和 deadline 算出等待边界，
而不是固定窗口。区别是这里「下一个到达」不是泊松假设，是每个 sequence 自己的确定性回投时间。
文献里没查到有人在 LLM decode 上做这一层预测；Metronome（2026）做的是按帧节拍 lock-step，
没有处理一帧内多步 decode 的相位问题。

## 端到端对比

LLM 与 TTS 各一个共享 executor 在 2 号卡，编码器在 3 号卡，Token2Wav 独占 4 号卡。loadsim 在节点内直连，每帧 1000 ms（与产品前端一致），trickle 到达 15 秒内铺开，每
session 固定 70 秒，整场 95 秒，随机种子固定，system prompt 与 `length_penalty` 用产品默认。
判据：决策延迟（从发出第 k 帧到收到模型对第 k 帧的 listen 或 text）p95 不超过 1 秒。

每个并发点都重启服务再测，两种策略同一随机种子。`w` 是实际合批宽度（平均每次 forward 合了
几个 step），`busy` 是 LLM 卡上 forward 时间占墙钟的比例，`hold` 是自适应策略主动扣住队列的
总时长。

### 结论

单卡 H20、o4.5 F16 权重、**固定人口形态**（会话一次投满、每个跑固定时长、没人中途退出补位）
下，决策延迟 p95 不超过 1 秒的上限是 **80 路，84 路是拐点，88 路不达标，两种策略一样**。
注意这一节的结论只对这个形态成立：换成会话持续生灭的真实到达形态，自适应把上限从 80 抬到
84，见下面「换成真实流量到达模型之后」。自适应策略在 12 到 72 路把 p95 降 5% 到 25%，但那个区间
本来就有 3 到 10 倍余量；在决定上限的 80 到 88 路，它测不出差别。把预算收紧到 150 ms 时
这个改善才体现成并发数（上限 36 到 40，见下面「收紧预算后的上限」），200 ms 以上就没有了。

原因在执行器 trace 里（`OMNI_EXEC_TRACE=1`，88 路）：

- 队列几乎不空。贪心策略的 batch 平均 12.7 个 step、p95 46 个，81% 的 batch 里已经带着 prefill。
  没有碎片可以合，预测到达再扣住也就无从省下 forward。自适应策略这时每次只扣 3.5 ms、
  一场只扣 263 次，宽度只比贪心多 2% 到 10%。
- 每次 forward 的成本由 prefill token 数决定，每 token 0.75 到 0.8 ms，与合了多少 step 无关。
  88 路每秒进 88 帧、每帧 11 token 的 prefill，光这一项就是每秒 700 到 800 ms 的 GPU 时间。
  这是算力墙，不是调度墙。
- 把 p95 顶过 1 秒的是个别耗时 1.7 秒的 batch（形状正常，21 到 231 token），不是调度间隙。
  排队等待的 p99 只有 300 ms。

服务时间曲线在 KV 位置 0 测的是乐观值。把 sequence 先填到位置 800 再测（q8_0 KV，4096
上下文）：单步 decode 从 6.8 ms 变 17 ms，32 路 decode 从 17 ms 变 82 ms，32 路 decode 加
32 路 prefill 混在一个 forward 里 502 ms。真实负载下 GPU 时间大部分花在 attention 读 KV 上，
合批省下的固定开销占比比曲线暗示的小得多。自适应策略的固定开销估计（在线从单步单 token
的 batch 学）在高负载下确实收敛到了 26 ms，所以它的判断没有错，只是没有东西可省。

真正把这张卡的上限从 24 路抬到 80 路的是这三件事，都不是调度：pool 模式建会话时不再清掉
所有人的 KV（之前 16 路以上必崩，且被清空上下文的会话每帧都说话，把负载形态整个改了）；
Token2Wav 挪到独立的卡（它每秒语音要 100 到 300 ms GPU，与 LLM 同卡时十几路就把卡吃满）；
每 sequence 上下文从 8192 降到 4096 并用 q8_0 KV，96 槽才放得进显存。

### 第二个变量：batch 大小与组成

上面的策略只动了「何时发」。「发多大」也试了：GPU 忙占比超过 0.5 时，decode 步先取，prefill
按到达顺序取到一个 token 上限为止，上限由在线估计的每 token 耗时反推、让一次 forward 落在
60 ms 上下（`OMNI_EXEC_BATCH_TARGET_MS`，也在 `adaptive` 策略里）。动机是每帧的三步链各等
一整轮队列，而一轮是 200 到 500 token 的 forward；把 prefill 切小，链里两次 decode 就不用
等在别人的 prefill 后面。

结果在 80 路直接崩：p95 从 0.5 秒变 16 秒，GPU 时间从 77 秒涨到 91 秒（busy 0.95），
1378 帧没等到决策。原因是位置 800 的曲线里那个数：一次 forward 哪怕只有一个 2 token 的步也要
17 ms，把 prefill 拆成更多次 forward 就是把这个固定开销乘上去；在上限附近系统受吞吐约束，
多出来的 15% GPU 时间直接把队列顶爆。同样的 Sarathi 式切分在 prefill 以千 token 计的
文本服务里有效，在这里每帧只有 11 token、固定开销占大头，方向反了。

两个变量都测过了：固定人口形态下时机在上限处无事可省，大小在上限处只能往大了走，而贪心已经
在那里。真实到达形态下时机是有东西可省的，见「换成真实流量到达模型之后」。

### 任何合批策略在上限处的收益上界

把 88 路贪心 trace 里纯 decode 的 batch 按宽度分桶：1 个 step 10 ms，8 个 17 ms，16 个 23 ms，
即每次 forward 固定开销约 9 ms、每 step 边际约 0.9 ms。这一场 95 秒发了 1677 次 forward，
每秒 17.6 次，固定开销合计每秒 158 ms，占 GPU 时间的 16%。这就是「合批」这个动作在上限处
能省的全部：哪怕把 forward 次数减到零也只多 16% 的 GPU，对应上限从 88 到 96 左右；而实际
可行的是把次数减一小半，自适应时机做到了减 10%，相当于 1.6% 的 GPU，在噪声以下。其余
84% 的 GPU 时间是 prefill token（每秒 968 个，每个 0.75 ms）和各 sequence 读自己的 KV，
与怎么分 batch 无关。

这个上界是从固定人口形态的 trace 里算出来的，它约束的是「在那个形态下还能省多少 GPU 时间」。
它不能搬到真实到达形态上：那里的瓶颈不是 GPU 时间总量不够，而是碎片化使得同样的 GPU 时间被
切成更多次 forward，队列排队时间因此涨上去。所以真实到达下自适应能把上限从 80 抬到 84，与这里
算出的 16% 并不矛盾——那 16% 说的是 forward 次数减到零能省多少算力，而真实到达下自适应赚的是
排队时间，不是算力。

### 收紧预算后的上限

上面的上限判据是产品用的 1 秒。自适应时机在中等负载下把 p95 降 5% 到 25%，这个改善在 1 秒
预算下体现不成并发数（那里余量 3 到 10 倍），但在很紧的预算下可能会。为了不让判据事后挑选，
预算先定死为 100、150、200、300 ms，再在 32 到 56 路（步长 4）、三个随机种子、同一套 96 槽
系统上测两种策略，上限取「三个种子 p95 的中位数不超过预算的最大并发」。

| 36 | 0.159 / 0.141 / 0.144 | 0.144 | 0.142 / 0.133 / 0.153 | 0.142 |
| 40 | 0.165 / 0.176 / 0.172 | 0.172 | 0.147 / 0.133 / 0.162 | 0.147 |
| 44 | 0.175 / 0.162 / 0.197 | 0.175 | 0.191 / 0.153 / 0.158 | 0.158 |
| 48 | 0.178 / 0.183 / 0.178 | 0.178 | 0.177 / 0.190 / 0.172 | 0.177 |
| 52 | 0.207 / 0.191 / 0.193 | 0.193 | 0.183 / 0.202 / 0.196 | 0.196 |
| 56 | 0.214 / 0.235 / 0.236 | 0.235 | 0.294 / 0.202 / 0.219 | 0.219 |

| 预算 | 贪心上限 | 自适应上限 |
|---|---|---|
| 100 ms | 无 | 无 |

21 个（并发，种子）配对点里自适应 p95 低于贪心的有 15 个，相对差的中位数 −6.1%。
只有 150 ms 预算下上限不同：40 路时三个种子自适应都在 0.165 s 以下、贪心都在 0.165 s 以上，
p95 中位数低 15%，正好跨过 150 ms 这条线，上限多一档（4 路，11%）。到 44 路以上两种策略
的差异落回种子噪声里（自适应 44 路种子 7 是 0.191，56 路种子 7 是 0.294，都高于贪心），
于是 200 ms 及更宽的预算下上限相同。

这是本项目里唯一一个「自适应时机抬高了 session 上限」的实测：条件是决策延迟预算 150 ms，
比产品用的 1 秒紧 6.7 倍，上限从 36 到 40，步长 4 的网格下差一档。在产品预算下结论不变。

### 换成真实流量到达模型之后

上面所有端到达对比用的到达形态是：会话在头 15 秒内陆续连上，每个固定跑 70 秒，没有人中途退出、
也没有人补位。并发爬到 N 之后就一直是 N。这是闭环容量测试的形状，不是压测工具里那套真实流量
模型（`--arrival poisson --reuse --lifetime-dist lognormal`：会话按泊松到达，时长服从右偏的对数
正态分布，退出后有人补位，稳态并发在目标值附近波动）。两者差四件事：没有会话中途生灭，因而没有
持续不断的建会话开销；并发被钉死而不是在目标附近随机起伏；所有会话年龄相同，因而 KV 位置相同，
而位置 0 与位置 800 的单步开销差 2.5 倍；会话时长是定值而不是右偏分布。

换成真实到达模型重测，先撞上两个与合批无关的问题，都得先解决否则测出来的数没有意义。

**一个会话滑动上下文窗口会冻结整个服务 11.1 秒。** 每个会话的上下文是 4096，用满到 2048 时
触发滑窗，滑窗把保留下来的 KV 往前挪，于是 llama.cpp 要做一次 K-shift。问题在于 K-shift 的图是
按整个 KV cache 建的（`build_graph_shift` 对 `get_size() * n_stream` 个 cell 逐层重算 RoPE），
而共享 executor 的 cache 是 96 个 sequence 合在一起的 393216 个 cell，q8_0 下还要反量化再量化。
实测每次固定 11.1 秒，期间 LLM executor 与所有会话的音频编码器全部静止。240 秒的一次压测里
触发 7 次，40 路并发的决策延迟 p95 就从 0.16 秒变成 5.7 秒，贪心与自适应各触发 7 次、结果一样。

之前所有的上限数据都没碰到这件事，因为那个形态下每个会话只活 70 秒、n_past 最多到 1005，够不着
2048 这个阈值。真实流量里会话时长是右偏的，长会话一定存在，这个冻结就一定会发生。下面的对比把
会话时长上限压到 140 秒来回避它，因为它对两种策略的影响完全相同、只会把策略差异淹掉。

**压测工具的补位跟不上，稳态并发卡在 29。** 补位模式下「会话退出后隔一段时间再补一个」这个等待
原本是在投放循环里串行 `await` 的，于是每秒最多补 `1/retry_mean`（默认 0.33）个会话。会话退出
速率是并发除以平均时长，目标一过 30 就超过这个上限，实际并发于是与目标脱钩：目标 32、40、48、
56 实测稳态分别是 25.8、28.8、28.7、29.2，而报告里仍然写着目标值。改成每次补位在自己的任务里
等，并给判定加了一条硬门禁：稳态并发不到目标的 85% 直接判 fail。

修完这两条之后重测，96 槽、每 sequence 4096 上下文、q8_0 KV，与上面的上限扫描同一套系统；
泊松到达加补位，会话时长对数正态、均值 70 秒、上限 140 秒，每点 300 秒、换新进程，种子 7。
稳态并发实测与目标相差 1% 以内，会话生灭在 300 秒里有 232 到 409 次。

|---|---|---|---|
| 48 | 0.251 s | 0.236 s | −5.8% |
| 56 | 0.354 s | 0.301 s | −14.8% |
| 64 | 0.508 s | 0.491 s | −3.5% |
| 72 | 0.579 s | 0.647 s | +11.8% |
| 80 | 0.716 s | 0.645 s | −9.9% |
| 88 | 2.889 s | 3.909 s | +35.3% |

80 路两种策略都通过、88 路都不通过，所以上限只可能落在 80 或 84。84 那一格用三个种子、
两种策略各测一遍，80 与 88 两端也各补到三个种子：

| 并发 | 贪心 p95（种子 7 / 11 / 23） | 判定 | 自适应 p95（种子 7 / 11 / 23） | 判定 |
|---|---|---|---|---|
| 80 | 0.716 / 0.937 / 0.687 | 三个都通过 | 0.645 / 0.686 / 0.647 | 三个都通过 |
| 84 | 6.635 / 4.954 / 5.797 | 三个都不通过 | 0.924 / 0.786 / 0.875 | 三个都通过 |
| 88 | 2.889（仅种子 7） | 不通过 | 3.909 / 1.633 / 2.027 | 三个都不通过 |

**决策延迟 p95 不超过 1 秒的上限：贪心 80 路，自适应 84 路。** 84 路那一格两种策略的六次运行
没有任何重叠，贪心落在 4.95 到 6.64 秒之间，自适应落在 0.79 到 0.92 秒之间，差 5 到 7 倍，
远大于同策略换种子的波动。未应答帧数同样分开：贪心 369 到 681 帧，自适应 12 到 25 帧。

两臂承担的负载是对齐的：84 路六次运行的稳态并发在 83.8 到 84.8 之间，客户端实际发出的上行帧
在 25046 到 27498 之间，自适应那一臂还略多一点（它没落后，会话按自己的时长正常结束，于是补位
次数多几次）。所以这不是自适应被喂了更轻的负载。

为什么真实到达下有收益、固定人口下没有：真实到达里会话一直在生灭，每个新会话要单独做一次
system prompt 的 prefill，到达时刻随机；加上并发在目标值附近起伏、各会话年龄不同因而 KV 位置
不同，队列里的步比固定人口形态碎得多。碎片是自适应策略唯一能赚的东西——固定人口跑到 80 路以上
时队列几乎不空、贪心已经平均合 12 个 step，没有碎片可合，所以两者打平。

需要说清楚这个数的边界：它成立的条件是会话时长上限 140 秒（为避开滑窗冻结），单卡 H20，
o4.5 F16 权重，96 槽、每 sequence 4096 上下文、q8_0 KV，电话语音形态的说话占比。84 比 80 高
5%，而 88 两种策略都塌，所以这一档就是自适应能拿到的全部。

### 音频加视频

前面的上限都是纯音频。用户指出真实产品是音视频双工,应当先在这个形态下比较。用压测工具的
音视频模式(每个 1 秒音频包附带一张 960x540 的 JPEG,与产品前端一致)重测,得到的结论与纯
音频相反:**动态合批时机不提高音视频的 session 上限,在拐点处反而更差。**

视频把每帧的 prefill 从 11 个 token(纯音频)抬到约 77 个(多出约 64 个视觉 token),再加上
编码器卡上每帧一次约 100 ms 的视觉编码。每帧的 GPU 时间因此由 prefill 算力主导,可供合批
时机回收的固定开销占比更小——正是「上限处收益上界」那一节的逻辑,视频把这个上界压得更低。

配置上有一处必须先处理:视频的 77 token/帧使得 4096 上下文在约 26 帧(26 秒)就撞上 2048 的
滑窗阈值,而一次滑窗冻结整个服务 11.1 秒(见「换成真实流量到达模型之后」)。把上下文放到
16384、会话时长上限压到 140 秒,滑窗在会话内不触发(实测每点 slides=0)。24 槽 16384 上下文
与 96 槽 4096 的显存占用相当,同一张卡放得下。到达形态、判据与纯音频那节一致。

先粗扫定位拐点(种子 7):

| 并发 | 贪心 p95 | 自适应 p95 |
|---|---|---|
| 4 | 0.335 s | 0.327 s |
| 8 | 0.523 s | 0.450 s |
| 12 | 0.767 s | 0.810 s |
| 16 | 13.829 s | 16.059 s |

12 通过、16 塌掉,拐点在 12 到 16 之间。14 用三个种子、两种策略各测一遍:

| 并发 | 贪心 p95(种子 7 / 11 / 23) | 自适应 p95(种子 7 / 11 / 23) |
|---|---|---|
| 14 | 1.318 / 2.957 / 崩溃 | 2.905 / 4.162 / 15.107 |

14 路两种策略都超 1 秒预算,而自适应在每一个可比的种子上都比贪心差(2.905 对 1.318、
4.162 对 2.957)。**决策延迟 p95 不超过 1 秒的音视频上限:两种策略都是 12 路,自适应没有
抬高,14 路处它反而更差。** 两臂的发压量对齐(稳态并发都是 14.6,发出的视频帧 4449 到 4631,
服务端自报视觉切片数与之匹配)。

自适应在 14 路更差的原因与它在纯音频高负载处「无事可省」是同一件事的加剧:视频负载下队列
早已被 prefill 塞满,主动扣住只增加延迟、没有 forward 可省,而这个形态在 14 路就到了纯音频
80 路才到的饱和状态。

结论对照:动态合批时机能不能抬高 session 上限,取决于负载里有多少「可合并的碎片」。纯音频、
真实到达形态下碎片够多,上限从 80 抬到 84;音视频形态下每帧的 prefill 重了七倍,碎片被算力墙
淹没,上限不动。到达模型和输入模态都是这个结论的一部分,单说「能」或「不能」都不完整。

### 三档设定：完全不合批、静态合批、动态合批

前面所有对比都是 `mixed` 对 `adaptive`,而 `mixed` 并不是「不合批」:它等待上限 3 毫秒,但队列里
只要出现任何一个 decode step 就立刻发,而这个条件在本负载下几乎永远成立,所以它合的是「此刻恰好
攒着的那些」。这等于把问题的三档设定压成了两档,而且贪心与自适应之间那点差值没有标尺——不知道
合批本身值多少,就无从判断动态调度值多少。

补上两档,执行器里新增两个策略:

- `none`:一次 forward 只带一个 step,从不等待。这是下界。
- `static`:等一个启动时读死的固定窗口(默认 10 毫秒),中途不因为队列里有什么而提前返回,
  也可以再配一个固定的步数触发条件。这是经典的固定合批窗口。

四档在同一套系统上跑同一组并发(音视频、真实到达、24 槽、16384 上下文、300 秒一点、种子 7):

| 并发 | 不合批 p95 | 静态 10 ms p95 | 贪心 p95 | 动态 p95 |
|---|---|---|---|---|
| 2 | 0.238 s | 0.316 s | 0.257 s | 0.244 s |
| 4 | 0.391 s | 0.382 s | 0.334 s | 0.319 s |
| 8 | 0.861 s | 0.517 s | 0.501 s | 0.446 s |
| 12 | 17.032 s | 0.819 s | 0.787 s | 0.784 s |
| 16 | 22.547 s | 15.399 s | 11.271 s | 16.338 s |

**决策延迟 p95 不超过 1 秒的上限:不合批 8 路,其余三档都是 12 路。** 也就是说合批这件事本身值
50% 的并发,而在「怎么合批」这一层,静态、贪心、动态三者的上限相同。

执行器自报的合批宽度(每次 forward 合了几个 step)与这一档消耗的 GPU 时间:

| 并发 | 宽度 不合批 / 静态 / 贪心 / 动态 | GPU 秒 不合批 / 静态 / 贪心 / 动态 |
|---|---|---|
| 2 | 1.00 / 1.12 / 1.04 / 1.07 | 63.2 / 60.2 / 63.3 / 63.2 |
| 4 | 1.00 / 1.28 / 1.08 / 1.17 | 113.5 / 98.8 / 114.9 / 104.8 |
| 8 | 1.00 / 1.75 / 1.34 / 1.37 | 243.6 / 183.0 / 209.5 / 207.3 |
| 12 | 1.00 / 3.01 / 2.17 / 2.31 | 389.5 / 285.1 / 328.1 / 319.6 |
| 16 | 1.00 / 5.07 / 4.00 / 3.93 | 340.1 / 329.6 / 372.5 / 356.9 |

三件事值得单独指出来。

**静态合批在低并发上是负收益。** 2 路时它的 p95 是 0.316 秒,四档里最差,比完全不合批的 0.238 秒
还高三成。固定 10 毫秒窗口在没有东西可合的时候是纯粹的额外延迟,而每帧要过三次队列,每次都交
这笔税。这正是「始终合批不是最优」的那一半。

**动态合批的价值不在它比静态更宽,而在它知道什么时候不该等。** 2 路时动态的 p95 是 0.244 秒,
与完全不合批的 0.238 秒基本相同:GPU 空闲时 busy 接近 0,等待的不等式永不成立,它自动退化成
不合批。8 路时它又变成四档里最好的 0.446 秒。同一套参数、不改配置,两端都在最优附近。

**静态最省 GPU,但省下来的算力换不成并发。** 每个并发档上静态的合批宽度都最大、GPU 时间都最低
(12 路时 285 秒对贪心的 328 秒,省 13%),可它的 p95 反而是三档合批里最差的。省下的是算力,付出
的是每个 step 固定多等的那一段,而决定上限的是延迟不是算力。

### 音视频下的服务端崩溃:根因是临时文件互相覆盖,已修

音视频压测里服务端段错误了五次(纯音频的全部运行里一次没有),调用栈都落在**音频**编码器
`audition_audio_batch_encode` 的 cuBLAS 矩阵乘里。看栈像是编码器卡上的并发问题,实际不是。

根因在服务端写临时媒体文件的地方。每个连接把上行音频和视频帧落到磁盘再交给编码器,而文件名
是 `audio_.<序号>.wav` 与 `image_.<序号>.jpg`,序号是**每连接**从 0 开始的计数,名字里没有任何
会话标识,目录又是全进程共用的一个 `/tmp/omni_ws`。于是所有并发会话写的是同一批路径。所有会话
都是每秒一帧,计数器齐步前进,冲突因此不仅必然发生而且是同时发生:一个会话正在读,另一个会话
把同名文件覆盖掉了。

读到截断的 WAV 多数情况下只是解码失败、打一行 `failed to read audio file` 就返回,这就是纯音频
运行只见错误日志不见崩溃的原因。读到截断的 JPEG 就不同了,它会解出一个尺寸不对的缓冲区,后面
的编码直接崩在矩阵乘里。崩溃只在音视频下出现,是因为只有开了视频才有 JPEG 这条路,而且每帧要
写两个文件,冲突率翻倍。

改法是给每个连接一个独立的临时目录(进程内原子计数命名),连接结束时整目录删掉,所有调用点一次
性覆盖。验证:先前连崩两次的那个点(贪心 14 路种子 23)修后连跑两次都正常结束;同一并发下媒体
文件读取错误从每次运行 29 次降到 0 次;运行结束后没有残留目录。

顺带确认这个缺陷没有污染前面的结论。贪心在修复后重测 4、8、12 路,p95 分别是 0.330、0.481、
0.790 秒,与修复前的 0.334、0.501、0.787 秒在噪声之内——每次运行 29 次损坏发生在约 4600 帧里,
占比太小,不足以改变汇总分位数。上面几张表因此仍然成立。

### 试过但没用:把等待的代价按队列深度计价

自适应的等待规则原本是「等 Δ 换 k 次 forward 的固定开销」,即 `Δ < k·F·busy·增益`。这条式子
把等待的代价算作一次,但实际上队列里每一个已排队的步都要陪着等,总代价是 Δ 乘队列深度。按这个
想法改成 `Δ·q < k·F·busy·增益`,预期是:低负载下 q 是 1 到 2、规则不变,保住中等负载的收益;
高负载下 q 变大、预算塌掉,策略自动退化成贪心,从而去掉它在拐点处输给贪心的那一段。

实测(音视频、真实到达、种子 7、新旧规则各一遍)结论是**没用**:

| 并发 | 新规则 p95 | 旧规则 p95 | 新规则扣住次数 | 旧规则扣住次数 |
|---|---|---|---|---|
| 4 | 0.327 s | 0.333 s | 983 | 774 |
| 8 | 0.483 s | 0.458 s | 2055 | 2284 |
| 12 | 0.780 s | 0.843 s | 2076 | 1954 |
| 14 | 2.662 s | 1.390 s | 1442 | 1420 |
| 16 | 14.953 s | 16.094 s | 1079 | 1099 |

关键证据是两列扣住次数:16 路时新旧规则分别是 1079 与 1099,几乎一样。**除数根本没起作用**,
因为 worker 每次 forward 都把队列抽干,等到它下一次做等待判断时,即便 16 路也只积了一两个步,
q 基本恒等于 1 到 2。14 路那一行的差距落在拐点的种子波动里(同一并发同一策略换种子实测在 1.3
到 14.4 秒之间),不是规则带来的。

这条线索由此封口:等待规则的代价项不是瓶颈。合批宽度本来就不是由「等多久」决定的,而是由上一次
forward 跑多久、期间攒了多少步决定的——这也解释了为什么静态、贪心、动态三档在高负载下宽度收敛。
`OMNI_EXEC_HOLD_QUEUE_COST` 保留为默认关闭的开关,只为让这次测量可复现。

## 继续优化该往哪走:四个实验

上面的结论是「四档合批在音视频下上限都是 12」。之后又做了四个实验找下一步方向,结论是
**合批这条线已经到底,剩下的杠杆在视觉 token 的数量上**,并给出了量化的换算关系。

### 实验一:上限处一帧的时间去了哪

执行器每批打一行 trace,记合了几个 step、多少 token、forward 实际耗时、这批里各 step 排了多久队。
12 个 session 的音视频负载跑 180 秒,共 4920 次 forward、9289 个 step:

| | p50 | p90 | p95 | 最大 |
|---|---|---|---|---|
| 一次 forward 耗时 | 22.0 ms | 70.5 ms | 102.6 ms | 248 ms |
| 每步排队等待 | 9.1 ms | 43.3 ms | 58.7 ms | 123.9 ms |
| batch 宽度 | 1.0 | 4.0 | 5.0 | 10 |

单个 step 平均由 22.3 ms 排队加 19.7 ms 分摊计算构成,等待占 53%。执行器自报的 GPU 忙占比
中位 0.95、p95 0.99。

**这两个数合起来解释了为什么四档合批打平:GPU 已经 95% 忙,而 batch 宽度中位数是 1。**
12 个 session 每秒产生约 24 个 step,forward 每秒完成约 25 次,到达速率与完成速率基本相等,
队列形不成,合批没有东西可合。那 53% 的等待也不是调度留下的空隙,是在等 GPU 跑完别人的
forward。等待规则调得再聪明也不会变,能动的只有 GPU 的总工作量。

### 实验二与三:GPU 时间对每帧 token 数是仿射的

固定 12 个 session,只改视频帧率(帧率低意味着只有一部分帧带图,平均每帧 token 数下降):

| 每帧 token | GPU 秒 | 决策延迟 p95 |
|---|---|---|
| 77.0(每帧带图) | 183.9 | 0.756 s |
| 28.6(四帧一图) | 111.0 | 0.222 s |
| 13.0(纯音频) | 81.9 | 0.095 s |

两端拟合出 `GPU 秒 = 61.2 + 1.594 × 每帧token`,中间那点回代得 106.8 对实测 111.0,差 4%。
按这个拆分,音视频负载的 GPU 时间里**视觉 token 占 55%,音频 token 占 11%,与 token 数无关的
固定部分占 33%**。固定部分是每次 forward 的开销、各 sequence 读自己的 KV、以及 decode 的计算。

再扫并发验证它换得到上限。0.5 fps 下(约一半的帧带图,每帧约 45 个 token):

| 并发 | p95 |
|---|---|
| 12 | 0.345 s |
| 16 | 0.470 s |
| 20 | 0.705 s |
| 24 | 0.978 s |

**1 fps 时上限 12,0.5 fps 时 24 仍然通过,帧率减半上限翻倍。** 24 已是这次配置的槽位上限,
所以 0.5 fps 的真实上限只知道不低于 24。这个杠杆的天花板由那 33% 的固定部分决定:视觉 token
降到零也只能把 GPU 时间从 183.9 降到 81.9,即最多 2.25 倍,对应上限最多到 27 左右。

### 实验四:静态窗口是拿延迟换 GPU,在饱和点附近汇率很差

判据预算是 1 秒而 p50 只用了 0.44 秒,看上去有延迟余量可换 GPU 时间,静态合批正是做这个交换的
旋钮。之前只测过 10 ms 一个窗口,并发网格又跳过了 14(贪心在 14 是 2.174 秒不达标),所以
「三档上限都是 12」有可能是网格太粗。把窗口在 14 个 session 上扫开:

| 窗口 | p50 | p95 | forward 次数 | 宽度 | GPU 秒 |
|---|---|---|---|---|---|
| 10 ms | 0.586 s | 1.583 s | 4324 | 3.68 | 284.5 |
| 30 ms | 1.016 s | 6.308 s | 2840 | 5.47 | 251.0 |
| 60 ms | 2.686 s | 12.449 s | 1995 | 7.50 | 220.4 |

窗口开大确实按合批的道理减少 forward 次数、降低 GPU 时间,10 ms 到 60 ms 少用 23% 的 GPU。
但延迟涨得远比窗口本身快:60 ms 的窗口每帧只该多加约 120 ms(每帧过两次队列),实测 p50 却从
0.586 秒涨到 2.686 秒。原因是饱和点附近每个 step 多等的那一段会乘上在飞的帧数,系统被推过了
服务率等于到达率的那条线。

结论两层。一是**没有任何窗口能让静态在 14 个 session 上达标**,所以四档上限同为 12 在加密网格
后仍然成立,不是网格粗造成的。二是**10 ms 窗口的静态合批在 14 个 session 上同时赢贪心两项**:
p95 1.583 对 2.174,GPU 284.5 秒对 345.3 秒少用 18%。静态在 12 个 session 时略差于贪心
(0.819 对 0.790),到 14 就反超,因为固定窗口那笔税在队列本来就深时相对变小,省下的 GPU 相对变大。

### 下一步

合批层面没有可做的了,原因不是「试过都没用」,而是有机制:上限处 GPU 95% 忙、队列形不成、
batch 宽度中位数是 1。

**有量化依据的方向是减少视觉 token 的数量,不是减少视觉编码的耗时。** 视觉编码跑在独立的编码器
卡上、利用率只有 13%,真正贵的是 LLM 把那 64 个视觉 token 做 prefill,占掉 55% 的 GPU 时间。
按实测的换算关系,每帧视觉 token 减半上限大致翻倍,直到撞上 33% 的固定部分、总共最多 2.25 倍。

落到产品上最直接的做法是视频帧率自适应:视频通话里画面大部分时间静止,相邻帧几乎一样时不必
送去重新编码和 prefill。上面这条曲线给出了它的收益上界与形状,不需要再猜。

### 断流

各表里的 starve 列没有列出，因为它在这批数据里不是容量信号。修掉播放缓冲的初始状态后，
剩下的断流会话都是同一个形状：每次模型开口的头 0.4 到 0.5 秒。第一个 Token2Wav chunk
在决策后 0.3 到 0.4 秒到达，第二个要再等 1 秒，中间客户端没东西可放。8 路和 88 路一样，
是 Token2Wav 流水线的启动延迟，与并发无关。

## 路上修掉的四个缺陷

这四个都不是 batching 本身的问题，但不修就没有可信的对比。

**合批后取 logits 的下标错了。** executor 把「输出行号」传给 `llama_get_logits_ith`，而它要的是
「batch 内 token 下标」。batch 里只要有一个多 token 的步，后面的 sequence 拿到的就是别人的
logits，日志里每次运行成千条 `invalid logits id`。这个 bug 从 stage 2 引入共享 executor 时就在，
之前所有多 session 结果都是在它之下测的。修完用 `--verify 16` 把 16 路合批（纯 prefill、纯
decode、混合、各 sequence 位置不同）逐一与单步基准比，argmax 全部一致，错误行归零。

**pool 模式建会话时把所有人的 KV 都清了。** slot 复用时对 `ctx_llama` 调 `llama_memory_clear`，
而开了共享 executor 后所有 slot 的 `ctx_llama` 指向同一个 context。每来一个新会话，正在跑的
会话 KV 全部被清空，并且与 worker 正在执行的 `llama_decode` 没有任何同步。后果两条：一是跑到
16 路以上必定在某次 slot 签出后段错误（三份日志同一个签名）；二是被清过 KV 的会话上下文成了
空的，模型从此几乎每帧都说话。前几轮对比里 speak 帧占 60% 到 96%、session 分成「一直说」和
「一直听」两类，就是这个原因，修完后 speak 帧占 1% 到 2%。改成只清本 slot 自己的 sequence，
经 executor 与 worker 串行。

**多字节字符切在 token 边界时 JSON 序列化抛异常。** 服务端整个进程 abort。改用替换式的
错误处理。

**播放缓冲从会话建立就开始计欠账。** loadsim 的缓冲模型初始不在倾听态，一个模型全程只听的
会话被记成 100% 断流。改成初始倾听，并且收到 listen 时结清上一轮的欠账。

另有一个没修的：Token2Wav 多卡轮转（`OMNI_T2W_DEVICES`）在 session 关闭时堆损坏，日志在
`/data/wangkaiqi/logs/crash-t2w-multiowner-20260917.log`。本轮 Token2Wav 单卡。

cmake --build build-cuda --target llama-omni-server llama-omni-perf-exec-cost -j 32

# 服务时间曲线（2 号卡空闲时）
CUDA_VISIBLE_DEVICES=2 OMNI_EXEC_UBATCH=512 OMNI_EXEC_KV_UNIFIED=1 \
  build-cuda/bin/llama-omni-perf-exec-cost -m <gguf> --widths 1,4,8,16,24,32 --lens 1,5,12,80 --nseq 32

build-cuda/bin/llama-omni-perf-exec-cost -m <gguf> --verify 16 --widths "" --nseq 17
